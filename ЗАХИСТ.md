## 1. Що це за проєкт (1 абзац для захисту)

Вебзастосунок для виконання **трудомістких обчислювальних задач**. Задача —
розв'язання двовимірного рівняння Пуассона `−Δu = f` на одиничному квадраті з
нульовими граничними умовами Діріхле, методом скінченних різниць з ітераційною
схемою SOR. Балансувальник навантаження розподіляє задачі між кількома
серверами застосунків, є черга з оцінкою часу очікування, автомасштабування
пулу та панель адміністратора.

**Чому саме Пуассон:**
1. ТЗ прямо перелічує «метод скінченних елементів» як приклад — це з тієї ж родини.
2. Задача **ітеративна** → прогрес у відсотках справжній, а не імітація.
3. **Переривна** → скасування реально зупиняє обчислення.
4. **Регульована за складністю** → `n` та ітерації наочно показують ліміт трудомісткості.
5. Є **аналітичний розв'язок** `u = sin(πx)·sin(πy)` → показуємо справжню похибку.

## 4. Обчислювальне ядро (математика)

**Задача:** `−Δu = f` на `[0,1]²`, `u = 0` на межі.

**Дискретизація:** сітка `inner × inner` внутрішніх вузлів, крок `h = 1/(inner+1)`.
Кількість невідомих = `inner²`.

**Схема SOR:**
```
u_ij ← (1−ω)·u_ij + ω · ¼·(u_{i-1,j} + u_{i+1,j} + u_{i,j-1} + u_{i,j+1} + h²·f_ij)
```

**Права частина:** `f(x,y) = 2π²·sin(πx)·sin(πy)` — гладка, має аналітичний розв'язок
`u(x,y) = sin(πx)·sin(πy)`. Сід лише масштабує амплітуду (±3%), не додає шуму.

**Що повертається:**
- `delta` — максимальна зміна за ітерацію (критерій збіжності)
- `residual` — справжня нев'язка `max|f − A·u|`, де `A·u = (4u − сусіди)/h²`
- `maxError` — похибка відносно аналітичного розв'язку
- `converged` — `delta < tol`
- `profile` — профіль розв'язку вздовж центрального рядка

**Типові числа:** сітка 200×200, ω=1.9 → 1791 ітерація, похибка **1.9e-4**.

**Чому `h = 1/(inner+1)`, а не `1/(g−1)`:** інакше правий і верхній край області
зсунуті на `h`, і похибка зростає в ~80 разів (було 1.55e-2 → стало 1.9e-4).

```sql

jobs(id PK, user_id FK→users, status, n, max_iter, tol,
```

## 10. Ймовірні питання на захисті + відповіді

### Архітектура та балансування

**Q: Як саме працює балансування?**
A: Балансувальник (`src/lb.js`) — єдина точка входу. Він тримає пул процесів
`app-1…app-N` (`fork()`). При появі задачі `pool.pick()` обирає сервер з найменшим
навантаженням; серед рівних — найдавніше використаний (round-robin). Задача
передається через внутрішній HTTP на `127.0.0.1:910X/run`.

**Q: Чому не nginx як балансувальник?**
A: ТЗ дозволяє «сам веб сервер» у ролі LB. Наш LB — це Node-процес, який одночасно
віддає статику, REST API і керує пулом. Це простіше для лабораторної і дає повний
контроль над чергою та автомасштабуванням.

**Q: Що буде, якщо сервер застосунку впаде під час виконання?**
A: `tick()` (кожні 400 мс) знаходить задачі зі статусом `running`, чий `worker_id`
відсутній у пулі, і повертає їх у чергу зі статусом `queued` та етапом
«перепризначено». Задача виконається на іншому сервері.

**Q: Чому `worker_threads`, а не окремі процеси для обчислень?**
A: `worker_threads` — легші за процеси, спільна пам'ять не потрібна (передаємо
`workerData`), і event loop балансувальника не блокується. Сервери застосунків —
окремі процеси (`fork()`), бо це вимога «≥ 2 сервери».

**Q: Як масштабується система?**
A: Горизонтально: `autoscale()` додає сервер при появі черги (до `MAX_WORKERS=3`)
і прибирає після 45 с простою (до `MIN_WORKERS=2`). Ручне керування з адмінки
вимикає автоматику на 60 с (`holdAutoscale`).

**Q: Чому максимум 3 сервери?**
A: Обмеження задано в `MAX_WORKERS`. Для лабораторної 3 достатньо, щоб показати
і scale-up, і scale-down. Змінюється змінною середовища.

### Обчислення та ліміти

**Q: Чому саме рівняння Пуассона?**
A: ТЗ перелічує «метод скінченних елементів» як приклад. Пуассон — з тієї ж родини,
але скінченні різниці простіші й чесніші для демонстрації. Задача ітеративна
(прогрес справжній), переривна (скасування працює), регульована за складністю.

**Q: Як обмежується трудомісткість?**
A: Три рівні: (1) невідомих ≤ 250 000, (2) ітерацій ≤ 20 000, (3) бюджет
`невідомі × ітерації` ≤ 600 млн. Плюс таймаут 60 с на сервері. Перевірка на клієнті
(UX) і повторно на сервері (безпека) — інакше ліміт обходиться через curl.

**Q: Що таке SOR і чому ω=1.9?**
A: Successive Over-Relaxation — прискорена ітераційна схема. ω=1 — звичайний
Гаус-Зейдель, 1<ω<2 — прискорення. Для сітки 200×200 оптимальне ω≈1.9, збіжність
за ~1791 ітерацію. ω=1 не встигає за 2000 ітерацій.

**Q: Як рахується похибка?**
A: Аналітичний розв'язок `u = sin(πx)·sin(πy)` відомий, тому `maxError = max|u_num − u_exact|`.
Для сітки 200×200 це 1.9e-4.

**Q: Що таке `delta` і `residual`?**
A: `delta` — максимальна зміна за ітерацію (критерій зупинки). `residual` —
справжня нев'язка `max|f − A·u|` дискретної задачі. Це різні речі: мала `delta`
не гарантує малу нев'язку, тому показуємо обидві.

### Дані та безпека

**Q: Чому SQLite, а не PostgreSQL?**
A: Для лабораторної SQLite достатньо: нульова конфігурація, WAL-режим для
конкурентного читання, файл `data/app.db`. Схема переноситься на PostgreSQL
без змін (стандартний SQL).

**Q: Як зберігаються паролі?**
A: bcrypt, cost 10. У БД лише хеш. JWT підписується `JWT_SECRET`, живе 12 год.

**Q: Чи можна побачити чужі задачі?**
A: Ні. `broadcastJob()` надсилає події лише власнику (`job.userId`) та адміну.
Подія черги містить лише `{length, nextEtaSeconds}` — без ID. Прямий запит
`/api/jobs/:id` чужої задачі → 404. Перевірено тестом `test-isolation.js`.

**Q: Що з SQL-ін'єкціями?**
A: Усі запити параметризовані (`?`). Конкатенації рядків у SQL немає.

**Q: Чому самопідписаний сертифікат?**
A: Для localhost немає CA. У продакшені — Let's Encrypt + HSTS. Для лабораторної
самопідписаний достатній, щоб показати HTTPS/WSS.

### Черга та ETA

**Q: Як рахується ETA?**
A: `averageDuration()` — середня тривалість завершених задач. `queueSnapshot()`
ділить її на ємність пулу і множить на позицію в черзі. Це оцінка, не гарантія.

**Q: Що якщо всі сервери зайняті?**
A: Задача стає в чергу (`status='queued'`), клієнт бачить позицію та ETA.
Коли звільниться слот — `tick()` передасть задачу на сервер.

### Слабкі місця (чесно)

**Q: Чому «сервери» — це процеси, а не контейнери?**
A: У середовищі розробки Docker відсутній. Сервери застосунків — дочірні процеси
Node (`fork()`), що дає той самий ефект горизонтального масштабування на рівні
процесів. Для справжніх контейнерів потрібен окремий образ для `src/worker.js`
і `deploy.replicas` — у поточній конфігурації цього немає (див. README).

**Q: Чому немає тестів фронтенду?**
A: Фронтенд — SPA без збірки на чистому JS. Логіка мінімальна (рендеринг +
WebSocket). Основна складність — на бекенді, там і тести.

**Q: Що з конкурентним доступом до SQLite?**
A: WAL-режим дозволяє конкурентне читання. Запис серіалізується SQLite.
Для лабораторного навантаження цього достатньо.

**Q: Чому `omega` зберігається в БД?**
A: Щоб при перепризначенні задачі (після падіння сервера) вона виконувалась
з тими самими параметрами. Раніше `omega` лежав у `result_json` і губився.

## 11. 23 питання з Reports.txt — короткі відповіді

**1. HTML, розбір, DOM.** HTML — декларативна розмітка структури. Браузер:
байти → символи → токени → вузли DOM. DOM — дерево вузлів (`document` — корінь).
`<script>` без `defer` блокує парсинг. У проєкті DOM оновлюється з WebSocket без
перезавантаження.

**2. HTML5.** Семантичні теги (`header/nav/main/section`), `<video>/<audio>/<canvas>`,
типи форм (`email/number/date`) + валідація без JS, localStorage/IndexedDB,
WebSocket/Fetch/CORS, прибрано `font/center/frameset`. HTML5 — Living Standard.

**3. HTTP та методи.** Запит-відповідь поверх TCP, stateless. GET (отримати,
ідемпотентний), POST (створити), PUT (замінити, ідемпотентний), PATCH (частково),
DELETE (видалити), HEAD (без тіла), OPTIONS (CORS preflight). Коди: 2xx успіх,
4xx клієнт, 5xx сервер. У проєкті: `POST /api/jobs` → 201, `GET /api/jobs`,
`POST /api/jobs/:id/cancel`, 422 — невалідні дані, 429 — ліміт.

**4. HTTP/1.0 → 3.0.** 1.0 (1996): нове TCP на кожен ресурс, немає `Host`.
1.1 (1997): keep-alive, конвеєризація, обов'язковий `Host`, але HOL blocking.
2.0 (2015): бінарний framing, мультиплексування, HPACK, Server Push; HOL лишився
на рівні TCP. 3.0 (2022): QUIC поверх UDP, незалежні потоки, QPACK, 0-RTT,
connection migration.

**5. HTTPS, SSL/TLS.** HTTPS = HTTP + TLS. Симетричне (AES-GCM) для даних,
асиметричне (ECDHE) для обміну ключами, SHA-256 для цілісності. TLS 1.3 — 1-RTT.
Ланцюг довіри: сертифікат → CA → перевірка підпису, терміну, домену (SAN).
У проєкті: самопідписаний сертифікат, TLS :8443, WSS.

**6. WebSocket, WS/WSS.** Повнодуплексний канал поверх одного TCP. Починається
як HTTP з `Upgrade: websocket` → `101 Switching Protocols`. `ws://` — без шифрування,
`wss://` — поверх TLS. У проєкті: `wss://localhost:8443/ws?token=JWT` — прогрес
задачі та стан черги.

**7. Тришарова vs двошарова.** Двошарова: клієнт + сервер БД, товстий клієнт.
Тришарова: Presentation (браузер) → Application (сервери) → Data (БД). Переваги:
незалежне масштабування, безпека (БД недоступна ззовні), повторне використання.
У проєкті: браузер → LB → app-сервери → SQLite.

**8. REST.** Архітектурний стиль: client-server, stateless, cacheable, uniform
interface (ресурси = URI, дії = HTTP-методи), layered system. У проєкті:
`POST /api/auth/login` → token, `GET /api/jobs`, `POST /api/jobs`,
`POST /api/jobs/:id/cancel`, `GET /api/admin/overview`.

**9. DevOps-інструменти.** CI/CD (GitHub Actions), контейнери (Docker),
оркестрація (K8s), IaC (Terraform/Ansible), моніторинг (Prometheus/Grafana),
логування (ELK), секрети (Vault). У проєкті: `npm start` піднімає кластер,
CI на GitHub Actions.

**10. JavaScript.** Динамічна типізація, функції першого класу, однопотоковий
event loop (call stack + task queue + microtask queue), замикання, hoisting,
`this` залежить від виклику. Асинхронність: callbacks → Promises → async/await.

**11. Клієнтський JS: безпека.** Код у браузері не довірений. Same-Origin Policy,
CORS, CSP, XSS (екранування, `textContent`), CSRF (JWT у заголовку, не cookie).
Висновок: клієнтська валідація — лише UX, усі ліміти повторно на сервері.

**12. JS, ООП, прототипи.** Прототипне успадкування: `[[Prototype]]`, ланцюжок
пошуку властивостей. `class` — синтаксичний цукор. `new F()` створює об'єкт з
прототипом `F.prototype`. Інкапсуляція — `#private` поля (ES2022).

**13. TypeScript.** Надмножина JS зі статичною типізацією. Типи, інтерфейси,
generics, union/intersection, type narrowing, `strict: true`. Компілюється в JS.
Переваги: помилки на етапі компіляції, автодоповнення, безпечний рефакторинг.

**14. Angular.** Фреймворк Google, TypeScript-first. Компоненти, DI, RxJS,
модулі/standalone, Router, Forms. Двостороннє зв'язування `[(ngModel)]`.
Плюси: структура з коробки. Мінуси: важчий поріг входу, більший бандл.

**15. ElectronJS.** Chromium + Node.js. Main process (вікна, ФС) + renderer
(UI) + preload (`contextBridge`). Десктопні застосунки на веб-технологіях
(VS Code, Slack). Мінуси: розмір, RAM.

**16. React.** Компонентний підхід, JSX, однонаправлений потік даних, Virtual DOM
+ reconciliation, хуки (`useState`, `useEffect`, `useMemo`). Екосистема: Router,
Redux/Zustand, Next.js. У проєкті фронтенд на чистому JS — щоб запуск був однією
командою.

**17. Django.** Python, MVT, ORM, авто-адмінка, URLconf, middleware, CSRF/XSS/SQL
захист з коробки. Django REST Framework — серіалізатори, ViewSet. Для трудомістких
задач потрібен Celery + Redis.

**18. ES6+.** `let/const`, стрілкові функції, класи, шаблонні рядки, деструктуризація,
spread/rest, модулі, Promise, Map/Set. ES2017: async/await. ES2020: `?.`, `??`,
BigInt. ES2022: top-level await, `#private`, `.at()`.

**19. Node.js.** V8 + libuv, неблокуючий I/O, event loop (timers → poll → check).
CommonJS і ESM. CPU-bound задачі блокують loop → `worker_threads` (так зроблено
в проєкті). БД: `pg`, `mysql2`, `mongoose`, `node:sqlite`. Параметризовані запити.

**20. Docker.** Image (незмінний зліпок) + container (запущений екземпляр).
Dockerfile, volume, network, `docker compose`. Переваги: однакове оточення,
ізоляція, `--scale app=4`. У проєкті Docker відсутній — роль контейнерів
виконують процеси Node.

**21. Kubernetes.** Pod → Deployment → Service → Ingress. HPA — автомасштабування
за метриками (аналог `pool.autoscale()`). ConfigMap/Secret, liveness/readiness
probes (аналог `/health`). Self-healing, rolling update.

**22. Хмарні технології.** IaaS/PaaS/SaaS/FaaS. AWS (EC2, S3, RDS, ELB), Azure
(App Service, AKS), GCP (GCE, GKE, Cloud Run). Auto Scaling Group — підйом
інстансів за метриками. Наша архітектура (LB + stateless app + спільна БД) —
типова хмарна схема.

**23. Terraform.** IaC від HashiCorp. Декларативний HCL, граф залежностей,
`plan` → `apply`. Providers (aws/azurerm/google), state (S3 + DynamoDB lock),
modules. Так розгортаються 2+ сервери застосунків і балансувальник — вимога п.5
на реальній інфраструктурі.
